## Завершённые задачи этапа

### Перенос production

- `coffee_bot` и его PostgreSQL перенесены на `mail` в `/opt/coffee_bot`.
- `n8n`, worker, Redis и PostgreSQL перенесены отдельно в `/opt/n8n`.
- Старые контейнеры на исходном сервере остановлены; данные оставлены для временного отката.
- Публичные адреса работают через nginx Mailcow:
  - `https://dragonzzz.ru` — n8n;
  - `https://miniapp.dragonzzz.ru/miniapp` — Coffee Bot Mini App.
- Сертификатами управляет штатный ACME-контейнер Mailcow; оба домена добавлены в SAN.

### CI/CD

- Push в `main` и ручной `workflow_dispatch` запускают `.github/workflows/deploy-main.yml`.
- На сервере установлен `/usr/local/sbin/deploy-coffee-bot` из версионируемого `.github/deploy/coffee-bot-deploy.sh`.
- GitHub Actions использует отдельный SSH-ключ с `restrict` и forced command; произвольные SSH-команды этим ключом запрещены.
- Deploy выполняет fast-forward до `origin/main`, проверяет Compose, пересобирает контейнеры, ждёт healthcheck и проверяет `/api/health`.
- Конкурирующие deploy-запуски сериализованы GitHub concurrency и серверным `flock`.

### Mini App: экспорт заказов

- Экспорт активных заявок теперь сгруппирован по заказчикам.
- Одинаковые позиции объединяются только внутри одного заказчика, в том числе между несколькими его заявками одного периода.
- В модальном окне показываются имя заказчика, его позиции, промежуточная сумма и общий итог.
- Текст функции «Поделиться» использует ту же группировку.
- Неактивные заявки, как и ранее, не попадают в экспорт.

### Плановая публикация акций

- Production-расписание изменено на `friday 21:00`, timezone `Asia/Krasnoyarsk`.
- Перед каждой плановой отправкой уже выполняется принудительный логин и загрузка каталога.
- `.runtime/promotions-schedule.json` вынесен в bind mount и сохраняется при redeploy.
- Причина отправки устаревшего прайса 28 августа подтверждена логами: в 20:10 по Красноярску upstream API ещё вернул период до 28 августа; новый период до 4 сентября был зафиксирован только при обновлении в 00:35.

## Ключевые технические решения

- Бот, Mini App API и раздача статического frontend остаются в одном Node.js-процессе.
- Каталог Tasty Coffee кэшируется в общей памяти процесса; scheduler использует тот же catalog service с `forceRefresh=true`.
- Заявки и пользователи хранятся в PostgreSQL 16, данные production находятся в `/opt/coffee_bot/db_storage`.
- Логи и состояние scheduler хранятся соответственно в `/opt/coffee_bot/logs` и `/opt/coffee_bot/.runtime`.
- Traefik на целевой сервер не переносился: публичные `80/443` принадлежат Mailcow nginx.
- Coffee Bot опубликован на внутреннем адресе `172.22.1.1:3001`, n8n — на `172.22.1.1:5678`; nginx Mailcow проксирует к ним.
- Production `.env` не хранится в Git и сохраняется между deploy-запусками.
- Экспорт реализован на frontend по данным admin orders API; дополнительный backend endpoint не создавался.

## Известные проблемы и риски

1. **Scheduler не проверяет смену недельного периода.** Успешный HTTP-ответ upstream считается достаточным, даже если `pricesValidText` и `orderContext.key` относятся к прошлой неделе. После отправки слот помечается опубликованным и не повторяется.
2. **Время 21:00 пока не подтверждено как гарантированно безопасное.** Известно только, что 28 августа в 20:10 новый каталог ещё отсутствовал, а к 00:35 уже появился.
3. **Нет unit/integration тестов.** CI сейчас проверяет deploy и runtime health, но не выполняет тесты бизнес-логики до развертывания.
4. **Внутренние адреса nginx завязаны на gateway Mailcow `172.22.1.1`.** Изменение subnet Mailcow потребует синхронного обновления Compose и nginx-конфигов.
5. **Nginx и n8n production-конфигурации не версионируются в этом репозитории.** Их необходимо учитывать при восстановлении сервера.
6. **Параметры локальной PostgreSQL в `compose.yaml` заданы статически.** Следует перенести учетные данные БД в `.env` или Docker secrets без изменения существующих данных.
7. **Старый сервер пока содержит остановленные rollback-копии.** Нужен отдельный срок хранения и решение об окончательном выводе из эксплуатации.

## Опробованные подходы, которые не следует повторять без изменений

- Межсерверный `scp -3` зависал до фактической передачи. Миграция была выполнена через локальные временные архивы; временные копии после проверки удалены.
- На целевом хосте нельзя запускать отдельный Traefik на `80/443`: эти порты заняты Mailcow nginx. Используются отдельные nginx-конфиги Mailcow.
- Сеть n8n с `internal: true` отключила исходящий DNS и не применила ожидаемый port binding. Рабочий вариант — обычная приватная Compose-сеть без `internal: true`.
- Восстановление n8n dump от прикладного пользователя с `--clean` завершалось ошибками владения `pgcrypto` и `uuid-ossp`. Рабочая схема: создать extensions администратором, исключить extension entries из restore list и восстановить прикладные объекты от n8n-пользователя.
- `REASSIGN OWNED` для административной роли PostgreSQL затронул системные объекты и был отклонён; для восстановления использовалось корректное владение при `pg_restore`.
- Простое принудительное обновление каталога в пятницу 20:10 не гарантировало свежий недельный прайс, потому что upstream обновился позже.

## Следующие шаги

1. Вынести проверку свежести недельного контекста в отдельную функцию catalog/scheduler уровня.
2. Перед публикацией сравнивать полученный `orderContext.key` с последним опубликованным контекстом и валидировать дату из `pricesValidText`.
3. Если upstream всё ещё возвращает прошлый период, не отправлять сообщение и не отмечать слот опубликованным; повторять refresh в ограниченном временном окне с явными логами и лимитом попыток.
4. Расширить scheduler state ключом фактически опубликованного order context для каждого канала и обеспечить обратную совместимость текущего JSON.
5. Добавить unit-тесты для timezone/slot logic, retry, нескольких каналов и устаревшего `pricesValidText`.
6. Вынести чистые функции admin export из browser entrypoint и покрыть тестами группировку, сортировку, суммы и исключение неактивных заказов.
7. Добавить test job в GitHub Actions перед deploy job; deployment должен запускаться только после успешных тестов.
8. После следующей пятничной публикации проверить `catalog.sync.success`, `promotions.scheduler.published` и фактический срок действия прайса в message log.
9. Версионировать шаблоны nginx/n8n recovery-конфигурации либо добавить отдельный закрытый infrastructure repository.
10. После согласованного retention-периода проверить резервные копии и вывести старый сервер из эксплуатации.
